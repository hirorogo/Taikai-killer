# 実行環境前提 — サンドボックス無効・マシン破壊前提

Taikai-killer ハーネスの **実行環境に関する設計前提** を定義する。
この前提はパイプライン全体（README の 1〜6 セッション）の運用に先立つ大前提であり、
セキュリティ・権限・ホスト選定のすべての判断はここに従う。

---

## TL;DR（結論）

1. **サンドボックスは対象外（無効）で実行する。** エージェントはホスト上でフル権限（シェル・ネットワーク・ファイル・コード実行）を持つ。隔離・権限プロンプト・許可リストによる摩擦を設けない。
2. **マシン破壊前提で運用する。** ホストは「壊れてもよい使い捨て機」とみなす。破壊・汚染・データ消失を許容コストとして受け入れたうえで自律無限ループを回す。

> この2つはトレードオフではなくセット。サンドボックスを外す代わりに、**ホスト自体を犠牲にできる構成**にすることで安全性を担保する（隔離する対象を「プロセス」から「マシンそのもの」に引き上げる）。

---

## なぜこの前提を取るか

README が要求する動作特性は、サンドボックス前提と本質的に相性が悪い：

| README の要件 | サンドボックスとの衝突 |
|---|---|
| レートリミットの続く限り**無限でおこなう** | 権限プロンプト・隔離オーバーヘッドが無限ループの律速になる |
| **マルチエージェント・オーケストレーション**で並行実装 | 並列エージェントごとの隔離はコスト・複雑性が爆発する |
| 外部知見を**大量クロール**（Scrapling / playwright-mcp） | ブラウザ起動・任意ネットワークアクセスが隔離下で頻繁に弾かれる |
| **コード生成→実行→テスト**を通すまで続ける | 未知コードの実行が前提。サンドボックス内 false negative で「動いたつもり」が混入する |
| **止まったら自動で叩く / ratelimit復帰で再開** | 無人・無確認で進む前提なので、対話的な権限承認を挟めない |

→ 速度・自律性・再現性（実機と同条件での実行）を優先し、**隔離はプロセス単位で行わず、ホスト単位（破壊可能なマシン）で行う**。

---

## 受容するリスク（明示的に飲む）

このプロジェクトは以下を「想定内・許容済み」とする。発生しても**警告・確認・停止の対象としない**：

- 生成・取得したコード／スクリプトの**任意実行**によるホスト汚染・改変・破壊
- クロール対象への**大量アクセス**、認証試行、使い捨て認証情報のホスト上での露出
- ファイルシステムの破壊的変更、パッケージ汚染、設定の上書き
- エージェントの暴走・無限リソース消費（コスト/CPU/ディスク）

> これらは**使い捨て環境前提だから許容できる**。下記「禁止事項」を破ったマシンで起きた場合のみ、本前提の範囲外（=本当の事故）となる。

---

## 要求事項 — どういうマシンで動かすか

✅ **必須条件**（すべて満たすホストでのみ実行する）

- **使い捨て可能**: クラウド VM / VPS / 専用コンテナホストなど、**いつでも破棄・再作成できる**こと
- **再構築可能**: イメージ／スナップショット／IaC（cloud-init・Dockerfile・スクリプト）から**ワンコマンドで再生成**できること
- **価値あるデータを置かない**: 個人ファイル・本番DB・長期保存物を同居させない
- **認証情報は使い捨て・最小権限**: 置く場合はスコープを絞った短命トークンのみ。失効・ローテーション前提
- **ブラスト半径が閉じている**: そのホストが完全破壊されても、他システム・本番・課金に波及しないネットワーク/権限境界

推奨形態: 専用の throwaway VM（スナップショット運用）／ 隔離 VPS ／ 破棄前提のコンテナホスト。

---

## 禁止事項（運用ガード）

❌ **以下の環境では絶対に実行しない**：

- 個人用 PC・開発常用マシン
- 本番サーバ、本番認証情報・本番DBに到達できるホスト
- 他人のデータ・共有資産が載っているマシン
- 破棄・再作成手段が用意されていないホスト（=壊したら復旧できない機）

> 「サンドボックス無効」が許されるのは**マシン破壊前提が成立しているときだけ**。
> 破壊前提が成立しないホストでこのハーネスを動かすことは、本ドキュメントの**重大な前提違反**であり、全リスクが本物の事故になる。

---

## 復旧・再作成

破壊・汚染を検知したら**修復を試みず、マシンを破棄して再作成する**のを基本動作とする：

1. ゴールデンイメージ／スナップショット／IaC から新ホストを再生成
2. 設定（`*.json` スコープ定義・トークン）を再投入
3. 中断フェーズの JSON 出力（`result.json` 等）から resume して再開

> 「直す」より「捨てて作り直す」が速く確実。これが破壊前提運用の利点。

---

## パイプラインとの関係

- **オーケストレータ**は権限制御や隔離を実装しない。代わりに **resume / circuit-breaker / cost-tracker**（速度・暴走・コストの制御）に注力する（speca orchestrator 流用方針／Issue #1 参照）。
- ヒューマンレビュー必須セッションでの STOP は「安全のための隔離」ではなく「要件/戦略の妥当性確認」のために存在する。実行安全はホスト破棄で担保する。
